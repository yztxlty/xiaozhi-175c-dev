1. 先建立全局模型

这是运行在微控制器上的实时语音终端。Board 隔离硬件差异，Application 集中业务调度，AudioService 拥有音频任务和队列，Protocol 拥有远端会话，Display 把状态投影到屏幕。

3. 启动与初始化

3.1 app_main

main/main.cc 的 extern "C" void app_main() 由 ESP-IDF 调用。它初始化 NVS；当出现无可用页或版本变化时擦除并重建 NVS。随后取得 Application 单例，调用 Initialize()，最后进入不返回的 Run()。

nvs_flash_init()
  └─ 异常：nvs_flash_erase() → nvs_flash_init()
Application::GetInstance()
  ├─ Initialize()  // 建硬件、回调、定时器、网络
  └─ Run()         // EventGroupWaitBits() 主循环

3.2 Initialize 顺序

  1. 取得 Board，状态置为 Starting。
  2. 创建/配置 Display UI。
  3. 取得板卡 AudioCodec，初始化并启动 AudioService。
  4. 注册发送队列、唤醒词、VAD 回调。
  5. 注册状态监听器；监听器只设置状态变化事件位。
  6. 启动 1 秒时钟定时器。
  7. 注册公共/用户 MCP 工具。
  8. 注册网络事件回调，异步启动网络。
线程边界：LVGL、业务状态和协议控制不要在任意网络/音频回调里直接做重活；使用 EventGroup 或 Schedule() 回主任务。

4. Application：事件中枢

application.h 定义了固定事件位：网络连接/断开、发送音频、唤醒词、VAD、错误、激活完成、时钟、开始/停止聆听、状态改变。Run() 等待任意事件，读取后清除，再按顺序处理。

来源事件主循环动作
AudioServiceSEND_AUDIOPop Opus 包并调用 Protocol::SendAudio()。
唤醒词WAKE_WORD_DETECTED关闭旧播报，打开音频通道，发送唤醒词。
ProtocolERROR回 Idle，Alert 显示错误。
BoardNETWORK_CONNECTED启动激活任务，刷新状态栏。
外部/UISTART/STOP_LISTENING执行手动聆听流程。

Schedule() 是跨线程的串行化入口：闭包先进入互斥保护的 main_tasks_，再用 MAIN_EVENT_SCHEDULE 唤醒主循环。每秒更新状态栏，每十秒打印堆统计。

6. AudioService：实时音频管线

AudioService 用队列把 PCM 实时处理和网络 Opus 包隔开。PCM 大且对延迟敏感，Opus 小且适合作为网络边界。

任务职责同步
AudioInputTask读取 10 ms PCM，喂给唤醒词/处理器；测试模式按 60 ms 采样。音频 EventGroup 位。
OpusCodecTask编码发送包，解码播放包，必要时重采样。队列 + condition_variable。
AudioOutputTask消费播放队列，按需打开功放，输出 PCM。队列非空或停止。
  • 固定帧：16 kHz × 60 ms = 960 个单声道采样。
  • 背压：发送、解码、播放队列有上限，保护 RAM 和实时性。
  • AEC：Kconfig 在设备侧和服务端侧二选一，构造函数用预处理器禁止同时打开。
  • 唤醒词：ESP-SR/自定义实现位于 audio/wake_words/，Service 依赖统一 WakeWord 接口。

7. Protocol：WebSocket 与 MQTT + UDP

Protocol 定义 Start、Open/CloseAudioChannel、SendAudio 和 JSON/音频/连接/错误回调。Application 不感知底层传输。

8. Board：一套业务适配多种硬件

Board 是多态单例，实例类型由编译期的 create_board() 决定。选中的板卡源文件调用 DECLARE_BOARD() 提供唯一工厂实现。

网络公共层有 WifiBoard、Ml307Board、Nt26Board、DualNetworkBoard 等。具体板卡负责总线、LCD/OLED、Codec、按键、电源和对象装配；不负责语音业务。

8.1 1.75C 实际选择

sdkconfig.175c 打开 CONFIG_BOARD_TYPE_WAVESHARE_ESP32_S3_TOUCH_AMOLED_1_75C=y；Kconfig.projbuild 声明选项；main/CMakeLists.txt 把它映射到 BOARD_TYPE=esp32-s3-touch-amoled-1.75，并选择字体/emoji 与源目录。

9. Display 与 YGSoul

显示继承层次可概括为：

Display
├─ NoDisplay
└─ LvglDisplay
   ├─ OledDisplay
   └─ LcdDisplay
      ├─ SpiLcdDisplay
      ├─ RgbLcdDisplay
      └─ MipiLcdDisplay

Display 统一提供状态、通知、情绪、聊天、主题、状态栏和电源模式。DisplayLockGuard 用 RAII 调用 Lock/Unlock，保护 LVGL 操作。1.75C 的 CustomLcdDisplay 复用通用 LCD UI，只加入 YGSoul 背景色、角色图片、启动 Logo、聊天颜色和说话动画。

状态视觉投影

Idle角色待机浮动，状态栏显示网络/电池。
Speaking浮动周期缩短并增加缩放动画。
错误/通知状态文字、情绪和提示音。

10. MCP、Settings 与 OTA

10.1 MCP

McpServer 启动时注册公共和用户工具，例如音量、灯光、GPIO、拍照和显示控制。服务器的 type=mcp payload 经 Protocol → Application → McpServer，工具结果再经 Application → Protocol 返回。

10.2 Settings

Settings 把运行时配置放入 NVS 命名空间：Board 保存 UUID；MQTT 读取 endpoint、凭据、主题和 keepalive；OTA 读取服务地址与激活数据。

10.3 OTA

  1. 网络连接后后台 ActivationTask 创建 Ota，检查资源和固件版本并激活设备。
  2. 运行期升级下载固件写入 OTA 分区，验证后重启。

Flash 分区位于 partitions/v2/32m.csv 等文件；assets 可由 CMake 调用 build_default_assets.py 生成。

12. 关键业务时序

12.1 首次开机

app_main → NVS → Application::Initialize
  → Board / Display / AudioService
  → Board::StartNetwork (异步)
  → NETWORK_CONNECTED
  → Activating: Ota 检查/激活/InitializeProtocol
  → ACTIVATION_DONE → Idle

12.2 唤醒到回复

麦克风 PCM → WakeWord::Feed
  → WAKE_WORD_DETECTED → OpenAudioChannel
  → hello / server hello → Listening
  → PCM → Processor/VAD → Opus → send_queue → Protocol
  → STT JSON 显示用户文字
  → TTS start → Speaking
  → Opus → decode_queue → Decoder → playback_queue → 扬声器
  → sentence_start 显示 assistant → TTS stop → Listening/Idle

12.3 断网

Board 产生 Disconnected → Application 设置事件位 → 若在 Connecting/Listening/Speaking 则关闭音频通道 → 刷新状态栏 → 回 Idle。MQTT 另有重连定时器，但重连动作通过 Schedule 回主任务。

14. 代码观察点与排查指南

无响应

  1. 确认 Application::Run() 仍在等待事件而非任务崩溃。
  2. 确认状态迁移合法；非法迁移会打印 warning。
  3. 确认 AudioService 事件位、队列和背压。
  4. 确认 hello 是否超时、MQTT endpoint/WS 配置是否来自正确 NVS。
  5. 确认 Display Lock 和 LVGL 操作是否在正确线程。

编译成功但行为不像目标板

检查 sdkconfig 是否在 reconfigure 时真正合入；确认只有一个 CONFIG_BOARD_TYPE_* 为 y；确认 CMake 映射到目标目录。1.75C 与 1.75 共目录，GPIO 依赖宏，是首要检查点。

分析边界：本文以当前工作区源码为准，未展开 build 生成物、managed_components 外部组件内部实现和真实串口日志。进一步验证应结合 compile_commands.json、ESP-IDF 组件 API 与硬件运行日志。
