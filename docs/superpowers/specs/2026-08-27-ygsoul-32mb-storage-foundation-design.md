# 幽光 AI 设备 32MB Flash 存储基础设计

## 1. 目标与范围

本轮在不更换 32MB Flash、不增加外置存储的前提下，为后续表情动效、离线歌曲、系统设置和轻量小游戏建立可持续的存储基础，并保持双分区 OTA 能力。

本轮交付范围：

- 将两个 OTA 应用槽从 4MB 扩展为 6MB。
- 将只读资源分区调整为 6MB，并把幽光形象大图从应用程序迁入资源分区。
- 新增 12MB 可写内容分区，使用 FATFS 与磨损均衡。
- 建立内容目录、容量统计、配额检查、健康状态和安全写入基础能力。
- 提供首次迁移所需的备份、烧录、校验和恢复流程。
- 在真实设备上验证启动、对话动画、重启、OTA 分区和内容分区。

本轮不实现音乐播放器、系统设置页面、游戏下载业务和新的表情套装；这些功能只使用本轮建立的存储接口，不再次修改基础分区。

## 2. 当前基线

目标硬件为 Waveshare ESP32-S3 Touch AMOLED 1.75C，已确认具备 32MB Flash 和 8MB PSRAM。当前应用镜像约 3.45MiB，4MB 应用槽仅剩约 14%；当前 16MB Assets 实际使用约 2.72MiB。

现有幽光形象资源直接编译进应用镜像，主要占用约 664KiB：

- 启动形象约 424KiB。
- 无嘴高清底图约 230KiB。
- 三个嘴型合计约 10KiB。

当前设备已通过真机验证三嘴型差分说话动画。迁移后必须保持主体固定、默认闭嘴、说话时只切换嘴部差分图，不改变现有视觉和交互行为。

## 3. 分区设计

采用“6MB + 6MB + 6MB + 12MB”平衡布局。前 2MB 保留现有引导、分区表、NVS、OTA 元数据和 PHY 数据。

| 分区 | 类型 | 起始地址 | 大小 | 结束地址 | 用途 |
|---|---|---:|---:|---:|---|
| `nvsfactory` | data/nvs | `0x009000` | 200KiB | `0x03B000` | 工厂配置，原址保留 |
| `nvs` | data/nvs | `0x03B000` | 840KiB | `0x10D000` | 用户配置，原址保留 |
| `otadata` | data/ota | `0x10D000` | 8KiB | `0x10F000` | OTA 启动选择 |
| `phy_init` | data/phy | `0x10F000` | 4KiB | `0x110000` | 射频校准数据 |
| `ota_0` | app/ota_0 | `0x200000` | 6MiB | `0x800000` | 当前或候选固件 |
| `ota_1` | app/ota_1 | `0x800000` | 6MiB | `0xE00000` | 当前或候选固件 |
| `assets` | data/spiffs | `0xE00000` | 6MiB | `0x1400000` | 只读系统和 UI 资源包 |
| `content` | data/fat | `0x1400000` | 12MiB | `0x2000000` | 歌曲、游戏资源、封面和存档 |

所有地址显式填写，最后一个分区恰好结束于 `0x2000000`，不越过 32MB Flash。应用槽最大允许 6MiB，构建阶段设置对应的应用大小检查，超过上限必须失败，不能生成不可 OTA 的交付物。

## 4. Assets 只读资源方案

### 4.1 资源职责

Assets 只存放随固件版本发布、运行时只读、丢失后可由 USB/升级包恢复的资源：

- 字体、Emoji 和系统音效。
- 幽光启动形象、无嘴高清底图、嘴型和后续眼睛/眼泪等差分图。
- 内置应用图标、默认主题和小游戏内置公共资源。

用户下载的歌曲、关卡、皮肤和存档不得写入 Assets。

### 4.2 幽光资源迁移

幽光资源继续采用 LVGL 可直接读取的 CBin/RGB565A8 格式，保持 280×280 画布和现有透明度，不使用 GIF/APNG 解码。构建时将资源作为额外文件打入 Assets 包，运行时通过 Assets 映射接口取得只读地址，再由 `LvglCBinImage` 提供给 LVGL。

资源命名使用全局唯一扁平名称，兼容当前 Assets 构建器会压平子目录的行为：

- `ygsoul_boot.cbin`
- `ygsoul_companion_nomouth.cbin`
- `ygsoul_mouth_1.cbin`
- `ygsoul_mouth_2.cbin`
- `ygsoul_mouth_3.cbin`

运行时只保留资源描述对象和少量状态，不复制整张图片到堆内存。迁移目标是从应用镜像释放约 664KiB，使基础固件回落到约 2.8MiB，为后续功能代码保留约 3MiB 的应用槽增长空间。

### 4.3 失败处理

设备启动时必须先校验 Assets 索引和五个幽光必需资源。资源缺失、尺寸错误或映射失败时：

- 记录明确错误日志和缺失文件名。
- 不访问空指针、不反复重试、不导致看门狗复位。
- 回退到现有轻量内置 Emoji/纯文本界面，保证配网、升级和基本对话仍可操作。
- Assets 故障不触发 Content 格式化，两类分区互不影响。

## 5. Content 可写内容方案

### 5.1 文件系统

`content` 使用 ESP-IDF FATFS + wear levelling，挂载点固定为 `/content`。原因是目标数据主要是数百 KiB 到数 MiB 的顺序读取音频和资源包，FATFS 更适合文件管理、删除、容量统计和后续 USB/工具链维护。

首次迁移时由烧录流程明确擦除 Content 区域。启动挂载遵循以下规则：

1. 首次发现分区为空白时，允许初始化 FATFS。
2. 已存在文件系统但挂载失败时，禁止自动格式化，进入故障状态并保留数据。
3. 格式化修复只能由明确的本地维护操作触发，不能由普通启动或下载失败触发。

### 5.2 目录和配额

初始化后建立固定目录：

```text
/content/music/
/content/games/
/content/covers/
/content/save/
/content/tmp/
```

容量预算：

| 类别 | 上限 | 说明 |
|---|---:|---|
| 音乐 | 8MiB | 3–5 首，24kHz 单声道 Opus，约 48kbps，每首最长约 4 分钟 |
| 游戏资源 | 2MiB | 关卡、皮肤和数据；游戏引擎仍在固件中 |
| 封面、存档、配置 | 0.5MiB | 小文件集中管理 |
| 安全余量 | 至少 1.5MiB | 下载临时文件、文件系统开销和原子替换 |

任何下载开始前同时检查分类配额和总剩余空间。安全余量不足时拒绝新下载，并返回可展示的“空间不足”状态，不挤占 OTA、Assets 或 NVS。

### 5.3 最小接口

新增单一 `ContentStorage` 服务，第一阶段只提供存储基础能力：

- `Initialize()`：挂载、首次初始化目录并返回健康状态。
- `GetStats()`：返回总容量、可用容量和各分类已用容量。
- `CanReserve(category, bytes)`：同时执行分类配额与安全余量检查。
- `GetPath(category, file_name)`：校验文件名并生成分类内路径，拒绝 `..` 和跨目录路径。
- `GetHealth()`：返回 `Ready`、`Unformatted`、`Corrupt` 或 `Unavailable`。

后续下载统一采用 `/content/tmp/<id>.part` 临时文件，完整校验后再原子重命名到目标目录。断电遗留的 `.part` 文件可在启动后清理，但正式文件不因下载失败而被覆盖。

## 6. 启动与运行时流程

启动顺序固定为：

1. 初始化 NVS 和基础硬件。
2. 初始化并校验 Assets，只读映射幽光资源。
3. 初始化 ContentStorage；失败时记录状态但不阻断基本对话和 OTA。
4. 创建显示界面；幽光资源有效时使用高清底图和差分嘴型，否则使用轻量回退界面。
5. 对话状态继续沿用现有逻辑：默认显示闭嘴帧，语音播放期间轮播三个嘴型，结束后立即恢复闭嘴。

ContentStorage 不在 LVGL 回调或音频实时回调中执行目录遍历和容量扫描；容量统计缓存由受控任务更新，避免影响动画和音频流畅度。

## 7. 首次迁移与防变砖流程

此次分区边界变化不能作为普通 OTA 首次下发，必须通过 USB 串口进行一次协调迁移。禁止写入 eFuse、禁止关闭下载模式、禁止整片擦除。

### 7.1 烧录前备份

- 读取并保存完整 32MB Flash 镜像。
- 单独读取 `nvsfactory`、`nvs`、`otadata` 和 `phy_init`。
- 为备份和待烧录的 bootloader、partition-table、应用及 Assets 生成 SHA-256。
- 记录芯片 MAC、Flash 容量、当前提交号和串口名称。
- 校验备份文件尺寸和哈希后才允许写入。

备份保存在仓库外的带时间戳目录，不加入 Git。

### 7.2 首次写入

首次写入采用同一构建产物完成：

- 保留原地址的 NVS 和 PHY 数据，不擦除这些区域。
- 写入新分区表。
- 将同一份已验证应用镜像写入 `ota_0` 和 `ota_1`，保证任一槽都具备可启动镜像。
- 写入新 Assets 包。
- 仅擦除新的 Content 区域，为首次 FATFS 初始化提供空白介质。
- 重置 OTA 选择到 `ota_0`，然后重启并观察完整串口日志。

不得使用全片擦除；写入命令必须使用显式地址和显式文件。

### 7.3 恢复方案

若新固件无法启动：

1. 长按 BOOT 并复位进入 ROM Download Mode。
2. 使用烧录前备份恢复旧分区表、旧应用、旧 Assets 和 OTA 元数据。
3. 仅在 NVS/PHY 校验失败时恢复对应独立备份，避免无意义覆盖设备身份和用户配置。
4. 恢复后验证旧固件启动、屏幕、联网和对话。

由于 Secure Boot 和 Flash Encryption 当前均未启用，且 ROM Download Mode 保持可用，只要不写 eFuse、不关闭下载模式，软件迁移失败属于可恢复故障，永久变砖风险很低。

## 8. 测试与验收

### 8.1 自动化测试

按 TDD 顺序新增测试并先确认旧代码失败：

- 分区契约：分区名称、类型、起止地址、32MB 边界、双 6MB OTA、6MB Assets、12MB FAT Content。
- 资源契约：五个幽光 CBin 存在于 Assets 输入目录；板级代码不再链接对应大数组；运行时通过 Assets 加载。
- 资源完整性：CBin 头、尺寸、颜色格式和文件大小符合约束；三嘴型位置和透明通道保持一致。
- ContentStorage：首次空白初始化、正常重挂载、分类目录、路径穿越拒绝、配额边界、安全余量和损坏分区不自动格式化。
- 构建契约：应用镜像小于 6MiB，Assets 镜像小于 6MiB，分区镜像互不越界。
- 回归契约：默认闭嘴、说话开始/停止、底部文字颜色区分和现有幽光显示逻辑保持不变。

### 8.2 构建验收

- 目标板完整构建成功，无新增编译警告和链接错误。
- `git diff --check` 通过。
- 输出并记录应用和 Assets 的真实字节数及剩余空间。
- 解析生成的 partition-table 二进制，结果必须与 CSV 一致。
- 检查最终烧录参数，不包含 eFuse、关闭下载模式或全片擦除操作。

### 8.3 真机验收

暂不使用虚拟设备平台。真机依次验证：

- 冷启动和连续三次重启均成功，无复位循环。
- 屏幕启动形象、进入对话前跑马灯、默认闭嘴和说话嘴型均正常。
- 配网、联网、聆听、回复、音频播放和对话结束恢复闭嘴正常。
- 串口日志显示 Assets 校验成功、Content FATFS 挂载成功和容量正确。
- 写入测试文件、重启后读取、删除后空间回收正常。
- 模拟配额不足时拒绝写入，不损坏已有文件。
- 确认当前运行分区、另一 OTA 分区有效，并完成一次双槽切换测试。
- 断电重启后 NVS 中的设备配置和网络配置仍保留。

## 9. 完成标准

同时满足以下条件才允许合入主分支并推送 GitHub：

- 新分区表、Assets 迁移和 ContentStorage 均有自动化测试证据。
- 应用镜像、Assets 镜像和分区边界全部通过构建检查。
- 应用镜像相对当前基线明显缩小，目标约 2.8MiB；若偏差超过 10%，必须说明原因。
- 真机完整流程、双槽启动、数据保留和恢复入口验证通过。
- 不提交备份镜像、构建产物、密钥、日志或用户现有未跟踪文件。
- 用户人工验收通过后，才合并主分支、推送 GitHub 并清理隔离工作树。
